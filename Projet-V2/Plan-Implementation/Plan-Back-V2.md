# Plan-Back-V2 — Plan d'implémentation du back
Statut : [x] à approuver  [x] approuvé par : Alexandre Morozoff le 28/10/26 (points à valider acceptés selon leurs recommandations)

## Décisions du plan

### PB-01 — Organisation en paquets et classes principales

**Choix.** Un projet Maven dans back/, groupe `io.github.milkliz0rd`, artefact `portfolio-back`, jar final `portfolio-back.jar`, paquet racine `io.github.milkliz0rd.portfolio`. Sous ce paquet :

```text
PortfolioBackApplication          démarrage ; active les propriétés de configuration et la purge planifiée (PB-03)
controller/
  FormTokenController             POST /api/v1/form-tokens (E-01) ; aucune logique
  ContactMessageController        POST /api/v1/contact-messages (E-02) ; @Valid @RequestBody ; aucune logique
dto/request/
  ContactMessageRequest           record des sept propriétés ; retire les espaces de bord ; contraintes de validation
  StrictStringDeserializer        n'accepte qu'une chaîne ou null pour chaque propriété
dto/response/
  FormTokenResponse               record formToken, minDelaySeconds, expiresInSeconds
  ErrorResponse                   record status, error, message, timestamp, path, validationErrors
validation/
  ContactField                    contrainte : longueur maximale et nature du champ (ligne, texte, adresse)
  ContactFieldValidator           une seule raison par champ, dans l'ordre du contrat
  Whitespace                      retrait des 25 points de code White_Space en bord de valeur
  EmailSyntax                     syntaxe de l'adresse du contrat (section 3)
service/
  ContactService                  exécute la chaîne de filtres, puis confie le message à l'expéditeur
  FormTokenService                délivre et vérifie le jeton (PB-02)
  ContactOutcome                  vocabulaire fermé des issues de E-02 (PB-05)
  ContactOutcomeLog               écrit la ligne de journal unique de chaque E-02
antispam/
  ContactFilter, FilterVerdict    interface d'un filtre et son verdict : passer, prendre en silence, refuser
  ContactSubmission               le message validé, le champ piège, le jeton, la clé d'adresse IP
  HoneypotFilter                  champ piège
  FormTokenFilter                 jeton
  IpRateLimitFilter               limite par adresse IP (PB-03)
  DailyCapFilter                  plafond global (PB-03)
sender/
  MessageSender                   interface « expéditeur de messages »
  ContactMessage                  les cinq champs, après retrait des espaces de bord
  SendFailedException             échec d'envoi, de nature « échec » ou « délai dépassé »
  NoOpMessageSender               adaptateur de développement : n'envoie rien
sender/brevo/
  BrevoMessageSender              adaptateur Brevo (PB-04, PB-07)
  BrevoEmailRequest               corps JSON de l'appel à Brevo
  BrevoRestClientFactory          client HTTP du JDK, adresse de base, délais (PB-04)
web/
  SecurityHeadersFilter           les trois en-têtes de sécurité sur toute réponse
  AllowedOriginFilter             origine autorisée, requête préalable, en-têtes CORS (PB-06)
  RequestSizeLimitFilter          corps de E-02 limité à 64 Kio

  GlobalExceptionHandler          gestionnaire global unique : tout le format d'erreur (PB-06)
```

Règles : un contrôleur ne fait que lire la requête, appeler un service et choisir la réponse ; toute décision vit dans service/, antispam/ ou sender/. Pas de repository/ ni de mapper/ d'entité : il n'y a ni base ni entité. Les filtres de servlet sont des composants Spring ordonnés (en-têtes, puis origine, puis taille), qui limitent eux-mêmes leur chemin : ils sont ainsi chargés par les tests par tranche (PB-07). Les filtres anti-spam sont des composants ordonnés, injectés en liste dans ContactService : ajouter une couche, comme ALTCHA en TK-63, c'est ajouter une classe à antispam/, placée après le jeton et avant la limite par adresse IP, sans toucher au reste.

Pile, conforme à la section 4 de la conception technique : starters Spring MVC, validation et Actuator ; en test, le starter de test de Spring MVC. Le JSON passe par la bibliothèque que Spring Boot 4 fournit par défaut, Jackson 3. L'appel à Brevo utilise le client HTTP de Spring (RestClient), présent dans Spring Web, avec la fabrique de requêtes du client HTTP du JDK : aucun starter ni kit de plus. Version : la dernière mineure de Spring Boot 4 à la date de TK-06, soit 4.1 au 27/10/2026 (dernier correctif 4.1.2, du 22/10/2026), ou 4.2 si elle est sortie en version stable d'ici là, comme le demande la DoD de TK-06.

**Raison.** Le découpage suit les conventions retenues le 13/10/2026 (contrôleurs sans logique, service, DTO d'entrée et de sortie, configuration, gestionnaire d'erreurs global) et les quatre briques que la DoD de TK-03 demande de nommer : entrée HTTP, service de contact, chaîne de filtres, interface d'expéditeur et ses adaptateurs. Un paquet par responsabilité laisse chaque ticket du back travailler dans son paquet. Le groupe `io.github.milkliz0rd` suit l'usage pour un projet hébergé sous un compte GitHub : il n'écrit pas le domaine du site dans chaque fichier.

**Écartés.** Un seul paquet à plat : la chaîne de filtres et les adaptateurs s'y mélangeraient au contrôleur. Un paquet par fonctionnalité (« contact », « token ») : il contredit le découpage par couches des conventions retenues. La configuration CORS de Spring MVC : voir PB-06. La documentation d'API par annotations (`@Tag`, `@Operation`) avec springdoc : écartée, et c'est un écart aux conventions retenues, soumis à Alexandre (points à valider). Le contrat signé est la seule documentation des échanges (« Ce contrat est le seul point de jonction entre le front et le back ») ; une seconde description générée depuis le code pourrait s'en écarter ; springdoc ajoute une dépendance qui ralentit le démarrage à froid sur 0,1 CPU et expose des points (description d'API, interface de test) que la section 7 de la conception exclut (« aucun autre point d'administration »). Chaque contrôleur renvoie, dans son commentaire de classe, à l'échange du contrat qu'il implémente.

### PB-02 — Jeton de formulaire signé

**Choix.**

- **Contenu** : 24 octets, l'instant d'émission en millisecondes depuis l'époque Unix (8 octets, gros-boutiste), suivi de 16 octets tirés par `SecureRandom`. Rien d'autre : ni adresse IP, ni origine, ni donnée du visiteur.
- **Forme** : `v1.<charge>.<signature>`, où `<charge>` est la charge en Base64 URL sans remplissage (32 caractères) et `<signature>` le HMAC-SHA256, en Base64 URL sans remplissage (43 caractères), calculé sur les octets ASCII de `v1.<charge>`. Le jeton fait 79 caractères. Le préfixe `v1` permet de changer de format plus tard sans toucher au front, qui ne lit pas le jeton (E-01).
- **Signature** : `javax.crypto.Mac` avec l'algorithme `HmacSHA256`, une instance de `Mac` créée à chaque appel (la classe n'est pas sûre entre fils) ; aucune dépendance.
- **Secret** : `CONTACT_TOKEN_SECRET`, décodé en Base64 standard, 32 octets au moins. Absent, illisible ou trop court : le back refuse de démarrer, avec un message qui nomme la variable sans jamais en montrer la valeur (contrôle fait par FormTokenService à sa construction, pas par la validation des propriétés, dont le rapport d'échec afficherait la valeur). En préproduction et en production, Render génère lui-même la valeur à la création du service (PB-08) : 256 bits, distincts d'un service à l'autre, comme le demande A-26. `generateValue` ne s'applique qu'à une variable qui n'existe pas encore (référence des Blueprints) : une synchronisation du Blueprint ne remplace donc jamais un secret changé à la main. Ce tirage retire un geste de A-04 et de A-26, qui demandent à Alexandre d'y poser le secret de signature des jetons : point à valider. Le secret vit dans une variable de l'hébergeur, qui survit à la veille et aux redémarrages : un jeton délivré avant une mise en veille reste valable après le réveil.
- **Vérification**, dans cet ordre : jeton `null`, vide ou fait d'espaces → absent ; plus de 200 caractères, pas exactement trois parties séparées par un point, préfixe autre que `v1`, Base64 illisible, charge autre que 24 octets ou signature autre que 32 octets → falsifié ; signature recalculée différente, comparée par `MessageDigest.isEqual` (temps constant) → falsifié ; âge (instant de l'horloge du back moins instant d'émission) inférieur au délai minimal → trop récent (un instant d'émission dans le futur l'est aussi) ; âge supérieur à l'âge maximal → expiré ; sinon valide. Les bornes sont incluses : un jeton est accepté de `CONTACT_TOKEN_MIN_AGE` à `CONTACT_TOKEN_MAX_AGE` après sa délivrance, comme le contrat le demande (« au moins `minDelaySeconds` et au plus `expiresInSeconds` »).
- **Réponse de E-01** : `minDelaySeconds` = délai minimal arrondi à la seconde supérieure ; `expiresInSeconds` = âge maximal arrondi à la seconde inférieure (section 5 du contrat). E-01 n'est compté ni dans la limite par adresse IP ni dans le plafond.
- **Horloge** : un `Clock` UTC injecté (ClockConfig), que les tests remplacent par une horloge réglable.
- **Usage multiple** : un jeton valide peut servir plusieurs fois pendant sa validité. Le front ne le réutilise jamais (il l'oublie après chaque succès et chaque échec, section 6 du contrat) ; un robot qui le réutilise reste borné par la limite par adresse IP et le plafond.
- **Rotation du secret** : changer la variable chez Render redéploie le service et rend falsifiés les jetons en circulation ; le visiteur concerné voit une fois l'échec réessayable, et « Réessayer » demande un jeton neuf. La procédure est écrite dans le README du back (TK-18).

**Raison.** C'est le minimum qui atteste ce que CT-08 demande, un formulaire ouvert ni trop tôt ni trop tard, sans stockage : l'instant prouve l'âge, la signature prouve que le back l'a émis, l'aléa rend chaque jeton unique et imprévisible. Signer la forme encodée ferme la porte aux variantes d'encodage d'un même contenu. Tout est dans le JDK, comme l'exige la section 4 de la conception.

**Écartés.** Un JWT et sa bibliothèque : une dépendance et des en-têtes pour deux valeurs. Un jeton à usage unique : il faudrait garder en mémoire les aléas déjà vus, et le contrat ne connaît que quatre causes de refus du jeton (absent, falsifié, trop récent, expiré). Un secret tiré au démarrage : la veille invaliderait tous les jetons, contre CT-08 et la section 3 du contrat. Une précision à la seconde : le délai minimal de 3 secondes y perdrait jusqu'à une seconde.

### PB-03 — Compteurs en mémoire

**Choix.**

- **Ce qui compte** : un message que la chaîne laisse passer et que le back confie à l'expéditeur, que l'envoi réussisse ou non (section 5 du contrat). Un message refusé par la validation, pris par le champ piège, refusé pour son jeton, par la limite ou par le plafond ne compte ni pour l'une ni pour l'autre.
- **Limite par adresse IP** : `CONTACT_IP_LIMIT_PER_HOUR` messages (départ : 5) par fenêtre fixe d'une heure, ouverte au premier message compté de cette adresse ; le message suivant de la fenêtre est refusé (le 6e au départ). Structure : un `ConcurrentHashMap` de la clé d'adresse vers une fenêtre immuable (instant d'ouverture, nombre) ; la réservation se fait d'un seul geste atomique par clé (`compute`) : fenêtre absente ou expirée, nouvelle fenêtre à 1 ; fenêtre ouverte sous la limite, nombre plus un ; sinon refus.
- **Plafond global** : `CONTACT_DAILY_CAP` messages (départ : 50) par fenêtre fixe de 24 heures, ouverte au premier message compté ; le message suivant de la fenêtre est refusé (le 51e au départ). Structure : un instant d'ouverture et un nombre, protégés par un verrou unique (méthodes `synchronized`).
- **Réservation et restitution** : la limite par adresse IP puis le plafond réservent leur place au moment où ils laissent passer le message. Si un filtre suivant refuse, ContactService rend la place réservée par les filtres précédents, dans l'ordre inverse (aujourd'hui : le plafond refuse, la place de la limite par adresse IP est rendue, et une fenêtre revenue à zéro est supprimée). Un échec du prestataire ne rend rien : le message a été confié.
- **Purge** : une tâche planifiée dans le back, toutes les 60 secondes, supprime les fenêtres d'adresse IP expirées, une à une et de façon atomique ; une fenêtre expirée est aussi remplacée au premier message suivant de la même adresse. Une adresse IP reste donc en mémoire au plus une heure et une minute après l'ouverture de sa fenêtre, comme CT-12 le demande (« effacée à l'expiration de sa fenêtre d'une heure »). Cette tâche interne ne reçoit aucun trafic entrant : elle ne tient pas le back éveillé.
- **Taille** : une fenêtre d'adresse IP n'existe que pour une adresse dont un message a été compté dans l'heure et la minute qui précèdent, et le plafond borne les messages comptés dans une même fenêtre de 24 heures. Au passage d'une fenêtre du plafond à la suivante, les fenêtres d'adresse ouvertes dans la dernière heure de l'ancienne coexistent avec celles de la nouvelle : la table contient au plus deux fois `CONTACT_DAILY_CAP` adresses (100 au départ), et au plus `CONTACT_DAILY_CAP` hors de ces passages.
- **Remise à zéro** : tout vit dans la mémoire de l'unique instance ; la mise en veille et chaque redémarrage repartent de zéro, risque assumé par CT-08 et rappelé dans le README du back.
- **Clé d'adresse IP** (ClientIpResolver) : l'adresse est lue dans l'en-tête nommé par `CONTACT_CLIENT_IP_HEADER`, que pose le proxy de l'hébergeur. Si sa valeur est une liste séparée par des virgules, l'adresse retenue est l'élément de rang `CONTACT_CLIENT_IP_POSITION` compté depuis la droite (1, la dernière), c'est-à-dire la première que le visiteur ne peut pas forger. La valeur est lue par `InetAddress.ofLiteral` (Java 22 et plus), qui n'interroge aucun service de noms. Une adresse IPv4 est la clé telle quelle ; une adresse IPv6 est ramenée à son préfixe /64, qu'un même abonné reçoit en entier et dans lequel il peut changer d'adresse à volonté. Variable vide (développement), en-tête absent, rang hors de la liste ou valeur illisible : la clé est l'adresse de la connexion ; dans les trois derniers cas, un avertissement sans valeur est journalisé une seule fois par démarrage, signe d'un réglage à reprendre. Le traitement natif des en-têtes de proxy de Spring Boot est désactivé (`server.forward-headers-strategy=none`) : ClientIpResolver est le seul code qui lit ces en-têtes. Le réglage de préproduction se constate en TK-24 (Étape 10), celui de production en TK-59.

**Raison.** La fenêtre fixe ouverte au premier message est celle que le contrat signé décrit pour l'adresse IP ; la même règle pour le plafond garde un seul modèle, en mémoire constante. Une limite de 5 par heure et 50 par période d'éveil n'appelle aucune performance : un verrou par clé et un verrou global sont simples à prouver justes, y compris sous accès concurrent (test de PB-07). Le JDK suffit.

**Écartés.** Une fenêtre glissante (liste des instants) : plus stricte au passage d'une fenêtre à l'autre, mais la veille remet de toute façon les compteurs à zéro, et le vrai filet reste le quota du prestataire (300 par jour, CT-08). Une bibliothèque de limitation (Bucket4j, Caffeine, Guava) : une dépendance pour ce que le JDK fait en quelques lignes. Une fenêtre calendaire (minuit UTC) pour le plafond : le contrat parle d'une « fenêtre de 24 heures ». Le premier élément de `X-Forwarded-For` : le visiteur peut le forger, puisque le proxy ajoute à la liste au lieu de la remplacer (constat rapporté sur le forum de Render, voir PB-08). L'adresse de la connexion seule : derrière le proxy de Render, tous les visiteurs auraient la même.

### PB-04 — Variables d'environnement et valeurs de départ

**Choix.** Toute valeur réglable passe par une variable d'environnement. Le fichier `application.yaml` relie chaque variable à sa propriété avec sa valeur de départ (par exemple `${CONTACT_TOKEN_MIN_AGE:3s}`), pour que les noms du contrat soient repris lettre pour lettre sans dépendre des règles de correspondance automatique de Spring Boot. Les propriétés sont lues dans `ContactProperties` et contrôlées au démarrage : une valeur invalide empêche le back de démarrer, donc de passer le contrôle de santé de Render, et le déploiement échoue au lieu de servir mal. Aucun profil Spring : le même fichier sert partout, seules les variables changent. Aucun fichier de variables n'est versionné ; `.env` est ignoré par git.

Valeurs fixes, dans le code et non réglables : préfixe de l'objet de l'e-mail `[Portfolio] ` ; nom d'expéditeur `Formulaire du portfolio` ; fenêtres d'une heure et de 24 heures (fixées par le contrat) ; corps de E-02 limité à 64 Kio (PB-06) ; 20 fils de traitement au plus pour le serveur web (`server.tomcat.threads.max`), assez pour un trafic de quelques messages par jour et moins gourmand en mémoire que les 200 par défaut sur 512 Mo.

Les durées s'écrivent avec leur unité, au format de durée de Spring Boot (`3s`, `2h`, `10s`) ; une durée écrite sans unité est lue en secondes. Les secrets et les adresses sont contrôlés par les classes qui s'en servent (FormTokenService, BrevoMessageSender) et non par la validation des propriétés, parce que le rapport d'échec de cette validation affiche la valeur refusée. Les types qui portent un secret ou une adresse redéfinissent leur représentation textuelle pour ne jamais les montrer.

**Raison.** La conception technique demande que tout soit réglable par variable d'environnement (D-07, section 4) et que les secrets ne vivent que chez l'hébergeur ; le contrat fixe sept noms, repris tels quels ; les autres variables suivent le même préfixe. Un adaptateur `brevo` par défaut fait échouer bruyamment un service mal configuré, au lieu de répondre `202` à des messages qui ne partiraient pas.

**Écartés.** Des profils Spring (dev, preprod, prod) : des valeurs dans des fichiers versionnés, dont l'adresse technique de la préversion du front, interdite dans le dépôt ; ce qui est propre à la production vit déjà dans son Blueprint (PB-08). L'adaptateur `none` par défaut : un oubli de configuration perdrait des messages en silence. Des valeurs de secret de développement versionnées : un secret, même factice, dans un dépôt public brouille la règle « aucun secret ».

### PB-05 — Journalisation

**Choix.**

- **Sortie** : la journalisation par défaut de Spring Boot, sur la sortie standard seulement, au niveau INFO, au format texte par défaut, que la console de Render affiche telle quelle. Aucun fichier, aucun journal d'accès du serveur web (désactivé par défaut et laissé ainsi : il écrirait les adresses IP).
- **Une ligne par requête POST sur la route de E-02**, sous le nom de journal `contact`, de la forme `contact-message outcome=<issue> durationMs=<durée>`, plus `fields=<champ>:<raison>,…` pour un refus de validation et `providerStatus=<code>` pour un échec du prestataire qui a répondu. Le code HTTP et l'adaptateur d'envoi n'y sont pas répétés : le premier se déduit de l'issue (PB-06), le second est écrit au démarrage. Les deux clés `durationMs` et `providerStatus` s'ajoutent à ce que le contrat demande (« la vraie issue et rien d'autre ») : les points à valider le signalent. Vocabulaire fermé des issues : `sent`, `validation-refused`, `unreadable-body`, `unsupported-media-type`, `not-acceptable`, `origin-refused`, `honeypot`, `token-missing`, `token-forged`, `token-too-recent`, `token-expired`, `ip-limit`, `daily-cap`, `provider-failure`, `provider-timeout`, `internal-error`. Les onze issues que nomme le contrat (section 1) y sont toutes ; cinq s'y ajoutent pour que chaque requête de E-02 ait sa ligne (corps illisible, type de contenu refusé, type de réponse refusé, origine refusée, erreur interne), ce que les points à valider signalent.
- **Qui écrit la ligne** : ContactService pour les issues de la chaîne et de l'envoi ; GlobalExceptionHandler pour la validation, le corps illisible, le type de contenu refusé (`415`), le type de réponse refusé (`406`) et l'erreur interne levée dans Spring MVC ; FallbackErrorController pour l'erreur interne remontée hors de Spring MVC (d'un filtre de servlet, par exemple) ; AllowedOriginFilter et RequestSizeLimitFilter pour les refus qu'ils rendent eux-mêmes. Chacun n'écrit que pour une requête POST sur la route de E-02. Chaque chemin se termine en un seul de ces endroits : une requête, une ligne. Les requêtes préalables `OPTIONS` et les appels à E-01 et E-03 ne sont pas journalisés, même refusés : un `403` d'origine sur E-01 ou sur une requête préalable, ou une erreur interne sur E-01, n'écrit aucune ligne.
- **Niveaux** : INFO pour les issues dues au visiteur (`sent`, validation, corps, type de contenu, type de réponse, origine, piège, jeton, `ip-limit`) ; WARN pour `daily-cap`, `provider-failure` et `provider-timeout`, qu'Alexandre doit remarquer (CT-14) ; ERROR, avec la trace d'exécution, pour `internal-error`.
- **Au démarrage** : l'adaptateur d'envoi actif et le nombre d'origines autorisées, jamais leur valeur ; un avertissement si l'adaptateur est `none` ; la durée de démarrage que Spring Boot écrit déjà (« Started … in … seconds »), qui sert aux mesures de TK-14 et TK-24.
- **Jamais dans un journal** : un champ du formulaire, une adresse e-mail (ni celle du visiteur, ni la destination, ni l'expédition), une adresse IP, la valeur d'un en-tête (`Origin` compris), le jeton, le secret, la clé de Brevo, le corps d'une réponse de Brevo (qui peut citer une adresse), le message d'une exception de lecture du JSON (qui peut citer un extrait du corps). Les exceptions du code du back ne portent jamais de donnée de la requête dans leur message.

**Raison.** Le contrat demande « une ligne par requête E-02, qui nomme la vraie issue et rien d'autre », seul endroit où Alexandre lit pourquoi un envoi a été refusé ; CT-12 et la DoD commune excluent toute donnée personnelle. Des paires clé-valeur stables se cherchent facilement dans la console de Render. La durée de traitement n'est pas une donnée personnelle et montre un prestataire lent ou un réveil.

**Écartés.** Des journaux structurés en JSON : lisibles par une machine, mais Alexandre les lit dans une console, sans outil d'agrégation. L'adresse IP hachée dans les journaux : une adresse IPv4 hachée se retrouve en essayant les quatre milliards possibles. Journaliser chaque E-01 : du bruit, et une trace de chaque visite du formulaire.

### PB-06 — Erreurs et réponses du contrat

**Choix.** Un gestionnaire global unique, GlobalExceptionHandler, hérite du gestionnaire standard des exceptions de Spring MVC (`ResponseEntityExceptionHandler`) pour que chaque exception connue de Spring garde son code HTTP, et remplace le corps par `ErrorResponse`. Le format est celui du contrat : `status`, `error` (libellé standard du code, `HttpStatus.getReasonPhrase()`), `message`, `timestamp` (instant de l'horloge, tronqué à la seconde, écrit en ISO 8601 avec le suffixe `Z`), `path` (chemin de la requête, sans hôte ni paramètre), `validationErrors` (objet ou `null`, toujours écrit, même à `null`). Le type de contenu `application/json` est imposé sur toute erreur, quel que soit l'en-tête `Accept`. Les filtres de servlet écrivent le même format par ErrorResponseWriter ; une erreur qui sortirait de Spring MVC passe par FallbackErrorController, qui remplace la page d'erreur par défaut de Spring Boot. Aucune réponse ne porte `Retry-After`.

| Situation | Produite par | Code | `message` | `validationErrors` | Issue journalisée |
| --- | --- | --- | --- | --- | --- |
| E-01 réussi | FormTokenController | 200, corps de E-01 | — | — | — |
| requête préalable `OPTIONS` d'une origine autorisée, sur E-01 ou E-02 | AllowedOriginFilter | 200, sans corps | — | — | — |
| en-tête `Origin` hors de `CONTACT_ALLOWED_ORIGINS`, sur toute route sous `/api/v1/`, requête préalable comprise, avant tout autre traitement | AllowedOriginFilter | 403 | `The request is not allowed.` | `null` | `origin-refused` pour un POST de E-02 seulement ; rien pour E-01 ni pour une requête préalable (PB-05) |
| E-02 : JSON mal formé, corps vide, valeur ni chaîne ni `null`, corps qui n'est pas un objet, corps de plus de 64 Kio | GlobalExceptionHandler (lecture du corps), RequestSizeLimitFilter (taille annoncée) | 400 | `The request body could not be read.` | `null` | `unreadable-body` |
| E-02 : refus de validation | GlobalExceptionHandler (validation de `@Valid`) | 400 | `One or more fields are invalid.` | une clé par champ en cause, dans l'ordre du formulaire | `validation-refused` |
| E-02 : champ piège rempli | ContactService | 202, sans corps | — | — | `honeypot` |
| E-02 : jeton absent, falsifié, trop récent ou expiré ; limite par adresse IP ; plafond | ContactService, puis ContactUnavailableException | 503 | `The service is temporarily unavailable.` | `null` | `token-…`, `ip-limit`, `daily-cap` |
| E-02 : Brevo en échec (réponse hors 2xx, erreur réseau) ou plus lent que son délai | ContactService, puis ContactUnavailableException | 503 | `The service is temporarily unavailable.` | `null` | `provider-failure`, `provider-timeout` |
| E-02 réussi | ContactService | 202, sans corps | — | — | `sent` |
| route inconnue | GlobalExceptionHandler | 404 | `The requested resource does not exist.` | `null` | — |
| méthode non prise en charge | GlobalExceptionHandler | 405, avec `Allow` | `The request method is not supported.` | `null` | — |
| type de contenu autre que `application/json` sur E-02 | GlobalExceptionHandler | 415 | `The request content type is not supported.` | `null` | `unsupported-media-type` pour un POST de E-02 (PB-05) |
| type de réponse demandé que le back ne produit pas | GlobalExceptionHandler | 406 | `The requested response type is not supported.` | `null` | `not-acceptable` pour un POST de E-02 seulement ; rien sur une autre route (PB-05) |
| toute autre exception | GlobalExceptionHandler (levée dans Spring MVC), FallbackErrorController (remontée hors de Spring MVC) | 500 | `An unexpected error occurred.` | `null` | `internal-error` pour un POST de E-02 seulement, écrite par celui des deux qui produit la réponse (PB-05) |
| E-03 hors d'état | Actuator | 503, corps de l'indicateur de santé | — | — | — |

Les réponses `202` du piège et de l'envoi réussi sont identiques : même code, aucun corps, aucun `Content-Type`, mêmes en-têtes. Toutes les réponses `503` de E-02 ont le même corps, horodatage mis à part.

**En-têtes** : SecurityHeadersFilter pose `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` et `Content-Security-Policy: frame-ancestors 'none'` sur toute réponse, E-03, erreurs et requêtes préalables comprises, y compris lors d'un renvoi d'erreur interne au serveur. AllowedOriginFilter, sur les seules routes sous `/api/v1/` : à une origine autorisée, `Access-Control-Allow-Origin` égal à l'origine reçue ; sur une requête préalable, en plus, `Access-Control-Allow-Methods: POST`, `Access-Control-Allow-Headers: content-type` et `Access-Control-Max-Age: 1800` ; `Vary: Origin` sur toute réponse de ces routes ; jamais de joker ni `Access-Control-Allow-Credentials`. Une requête sans `Origin` est traitée normalement (contrat, section 1). E-03 ne reçoit aucun en-tête CORS.

**Ordre de traitement de E-02** : en-têtes de sécurité ; origine ; taille du corps ; lecture du JSON ; validation ; champ piège ; jeton ; limite par adresse IP ; plafond ; expéditeur. C'est l'ordre du contrat (« la validation des cinq champs […], puis la chaîne de filtres […] — champ piège, jeton […], limite par adresse IP, plafond global »).

**Validation** : `@Valid @RequestBody` sur le DTO ; chaque champ porte une seule contrainte `@ContactField` (longueur maximale du contrat, nature ligne, texte ou adresse), dont le validateur produit au plus une violation, la première raison dans l'ordre `required`, `too-long`, `line-break`, `invalid-email`, avec le code de raison pour message. Le DTO retire les espaces de bord dans son constructeur, avec la classe `\p{IsWhite_Space}` en début et en fin de valeur (les 25 points de code du contrat, ni `trim()` ni `strip()`), sur les cinq champs et le champ piège ; le jeton est gardé tel quel. Les longueurs sont celles de `String.length()`. L'adresse suit la grammaire « valid e-mail address » du standard HTML, avec au moins un point dans la partie après l'arobase, en caractères ASCII seulement ; un retour à la ligne dans l'adresse donne `invalid-email`. Un désérialiseur strict refuse toute valeur qui n'est ni une chaîne ni `null` (le JSON accepterait sinon un nombre converti en texte), et le DTO ignore les propriétés inconnues de façon explicite, sans dépendre des réglages par défaut de Jackson.

**Taille du corps** : RequestSizeLimitFilter refuse un corps annoncé de plus de 64 Kio et borne la lecture d'un corps sans longueur annoncée (une lecture qui dépasse échoue, ce qui donne le même `400`). Un corps valide fait au plus environ 17 Kio (5 000 caractères de trois octets au plus en UTF-8, plus les autres champs).

**Raison.** Un gestionnaire unique est la règle des conventions retenues et du contrat (« Format d'erreur, unique pour toutes les erreurs du back ») ; hériter du gestionnaire standard évite d'oublier un code de Spring. Un filtre CORS écrit pour le contrat donne exactement les en-têtes demandés : la prise en charge CORS de Spring MVC rejette une origine par un texte brut (`Invalid CORS request`, contrat, section 8) et pose trois valeurs dans `Vary` au lieu de la seule `Origin` du contrat. Une contrainte personnalisée garde la règle des conventions (`@Valid @RequestBody`) tout en appliquant les règles du contrat, que les contraintes standard (`@NotBlank`, `@Size`, `@Email`) ne savent pas reproduire : retrait des espaces de bord propre au contrat, une seule raison par champ, codes en kebab-case, syntaxe de l'adresse. La limite de taille protège une instance de 512 Mo ; le refus prend la forme d'un `400` de corps illisible, issue que le contrat définit déjà, au lieu d'un code qu'il ne prévoit pas.

**Écartés.** La configuration CORS de Spring MVC avec un processeur de rejet remplacé : on garderait les trois valeurs de `Vary`. La validation écrite à la main dans le service, sans `@Valid` : contraire aux conventions retenues. Les contraintes standard : elles comptent les espaces de bord et peuvent donner plusieurs raisons par champ. Un `413` pour un corps trop gros : un code que le contrat ne prévoit pas. Le format `ProblemDetail` de Spring : ce n'est pas celui du contrat.

### PB-07 — Plan de tests

**Choix.** JUnit 5, AssertJ et Mockito, fournis par le starter de test de Spring MVC de Spring Boot 4. Trois niveaux, tous lancés par `./mvnw verify`, en local comme dans la CI (TK-07) :

- **Unitaires, sans Spring** : Whitespace (chacun des 25 points de code retiré en bord ; U+FEFF et U+001C conservés ; un caractère intérieur conservé) ; ContactFieldValidator (tableaux paramétrés : champ absent, `null`, vide, fait d'espaces ; longueur maximale exacte et dépassée de 1, émoji compté pour deux ; chacun des cinq caractères de retour à la ligne dans le nom, le prénom et le sujet, permis dans le message ; adresses valides et invalides, dont un domaine sans point, un caractère non ASCII et un retour à la ligne ; une seule raison, la première dans l'ordre) ; FormTokenService (jeton valide ; absent, `null` et vide ; falsifié : signature changée, charge changée, préfixe changé, Base64 illisible, longueurs fausses, autre secret ; trop récent à 2,999 s ; accepté à 3 s et à 2 h ; expiré à 2 h et 1 ms ; arrondis de `minDelaySeconds` et `expiresInSeconds` ; secret absent ou trop court refusé au démarrage sans que le message contienne la valeur) ; IpRateLimitFilter (fenêtre ouverte au premier message ; 6e refusé ; nouvelle fenêtre une heure après ; restitution ; purge ; 50 appels simultanés sur une même adresse avec une limite de 5 donnent exactement 5 passages) ; DailyCapFilter (51e refusé ; nouvelle fenêtre après 24 heures ; restitution ; appels simultanés) ; ClientIpResolver (en-tête absent ; liste avec un premier élément forgé ignoré ; rang 1 et rang 2 ; IPv6 ramené au /64 ; valeur qui n'est pas une adresse ; variable vide) ; ContactService (ordre de la chaîne ; piège : aucun envoi ; chaque refus : aucun envoi et place rendue ; échec du prestataire : place gardée). E-01 : `200`, corps et en-têtes ; E-02 : `202` sans corps et un seul appel à l'expéditeur, avec les valeurs sans espaces de bord ; chaque raison de validation de chaque champ et l'ordre des clés ; `400` de corps illisible pour chaque cas de PB-06 ; `403` au format d'erreur sur E-01 et E-02, requête préalable comprise ; requête préalable autorisée : chaque en-tête exact ; requête sans `Origin` traitée ; les trois en-têtes de sécurité sur `200`, `202`, `400`, `403`, `404`, `405`, `415`, `500` et `503` ; aucun `Retry-After`, ni joker, ni `Access-Control-Allow-Credentials` ; `404`, `405`, `415` et `500` au format d'erreur. Succès (réponse `201`) ; échec (`400`, `401`, `500`, erreur réseau) → nature « échec » ; délai dépassé (le serveur simulé lève une exception d'expiration) → nature « délai dépassé » ; contenu exact de l'appel : méthode, chemin, en-tête d'authentification de Brevo, expéditeur (adresse de `CONTACT_MAIL_FROM`, nom fixe), destinataire unique (`CONTACT_MAIL_TO`), adresse de réponse égale à celle du visiteur, objet `[Portfolio] ` suivi du sujet, corps texte des cinq champs, aucun autre destinataire. Un test de plus, avec le serveur HTTP intégré au JDK (aucune dépendance), qui répond après 2 secondes à un client réglé sur 1 seconde, prouve que le délai est vraiment appliqué par le client réel : `provider-timeout` en moins de 2 secondes. Les adresses des tests sont fabriquées par le test, sans arobase écrite en clair dans le code.
- **Application complète (`@SpringBootTest`)**, deux tests seulement : le contexte démarre avec la configuration de test (DoD de TK-06) ; E-03 répond `200` et exactement `{"status":"UP"}`, sans `details`, ni `components`, ni `groups`, avec les en-têtes de sécurité et sans en-tête CORS ; `/actuator`, `/actuator/health/liveness`, `/actuator/health/readiness` et `/actuator/info` répondent `404` (page de découverte fermée par `management.endpoints.web.discovery.enabled: false`, sondes désactivées et seule la santé exposée, Étape 1).

**Écartés.** Tout en `@SpringBootTest` : plus lent, et contraire à la règle de la tranche web. WireMock ou MockWebServer : une dépendance de test pour ce que Spring et le JDK font déjà. Un seuil de couverture dans la CI : il pousse à tester ce qui compte peu.

**Constats en ligne, au 27/10/2026.** Render construit et exécute un service à partir du Dockerfile du dépôt, avec un chemin de Dockerfile et un contexte réglables et la construction en plusieurs étapes ; sa référence des Blueprints liste `free` parmi les offres d'un service web et `frankfurt` parmi les régions, sans exclure le runtime Docker de l'offre gratuite ; elle ne le confirme pas non plus en toutes lettres, ce que la création du service (A-04) tranchera (points à valider). ### PB-09 — Adresse du back de préproduction

**Choix.** Le back de préproduction est joint par l'adresse technique que Render attribue au service (un sous-domaine du domaine de services de Render, dérivé du nom du service), sans domaine personnalisé. Cette adresse n'entre pas dans le dépôt : elle est posée dans la configuration de préproduction du front par le moyen que fixe le plan du front (TK-04, point 7), et dans le paramètre du contrôle de TK-49, hors du dépôt. Seule la production a son sous-domaine du site (CT-06), écrit dans son Blueprint (PB-08) et rattaché à la bascule (A-26, TK-59).

**Raison.** TK-24 a lieu en W13, alors que la zone DNS ne passe chez Cloudflare qu'avant W32 (A-09) : un sous-domaine de préproduction demanderait d'ajouter un enregistrement dans la zone d'OVH, puis de le recopier au déplacement de la zone. L'adresse technique existe dès la création du service, sans DNS ni certificat à attendre, et un changement d'adresse de la préproduction ne touche pas les visiteurs. Le sous-domaine de production reste celui qui compte pour changer d'hébergeur sans reconstruire le front ; il est vérifié par les contrôles de TK-49 à la bascule.

**Écartés.** Un sous-domaine du site pour la préproduction : un enregistrement DNS de plus avant le déplacement de la zone, et un nom de préproduction publié dans le DNS public, pour éprouver un chemin que la bascule éprouvera de toute façon. Le nom du service est écrit dans `render.yaml` et l'adresse technique s'en déduit : l'adresse n'est pas cachée pour autant, et la sécurité du back n'en dépend pas (origine autorisée, validation, filtres).

### PB-10 — Analyse statique

**Choix.** SpotBugs, par son greffon Maven, but `check` rattaché à la phase `verify` : effort maximal, seuil de confiance moyen, analyse du code principal (pas des tests), build en échec à la première anomalie. Les exclusions éventuelles vivent dans `back/spotbugs-exclude.xml`, vide au départ, chacune avec un commentaire qui dit pourquoi. La version du greffon est la dernière à la date de TK-06, puis suivie par le robot de mises à jour. Le même `./mvnw verify` lance compilation, tests, SpotBugs et paquetage, en local comme dans la CI (TK-07). Le greffon d'application des règles de Maven (enforcer) exige Java 25 (`[25,26)`) : le build échoue sur un autre JDK (DoD de TK-06).

**Raison.** SpotBugs analyse le code compilé et trouve des défauts réels (déréférencements nuls, accès concurrents mal protégés, utile pour les compteurs de PB-03, ressources non fermées) avec peu de réglages ; il tourne sur Java 25 (correctif de démarrage sur Java 25 disponible depuis la 4.10.1 : la 4.10.0, qui le portait, n'a jamais été publiée ; dernière version 4.10.5 du 11/10/2026) et ne demande aucun secret, ce qu'exige la DoD de TK-07.

**Écartés.** SonarQube Cloud : un jeton à stocker dans la CI. CodeQL : sans secret et gratuit pour un dépôt public, mais il ne tourne que sur GitHub, pas avec le build local ; Alexandre peut l'activer plus tard dans les réglages du dépôt, en complément hors du contrôle bloquant. Checkstyle : de la mise en forme, pas des défauts. PMD : des règles de style et de pratiques à trier longuement. Error Prone : un greffon du compilateur qui demande des options d'ouverture des modules de la JVM, au prix d'une configuration Maven plus fragile à chaque montée de JDK.

## Points à valider par Alexandre

- **Documentation d'API par annotations** : écart aux conventions retenues le 13/10/2026. Le plan n'ajoute ni springdoc ni `@Tag` et `@Operation` : le contrat signé est la seule documentation des échanges, et le back n'expose rien d'autre que ses trois échanges (PB-01). Autre écart, mineur : en plus des tests par tranche web, deux tests sur l'application complète (démarrage du contexte, demandé par TK-06, et indicateur de santé), et des tests unitaires sans Spring (PB-07). Recommandation : accepter.
- **Taille de TK-16 et TK-22** : le plan estime TK-16 à environ 770 lignes, tests compris, contre 330 dans Tickets-V2, et TK-22 à environ 590 contre 360. Recommandation : (1) créer dès maintenant un ticket complémentaire « Socle HTTP du back : format d'erreur, en-têtes de sécurité, origine autorisée » (Étape 3, environ 390 lignes, domaine back), en W5 à côté de TK-07, seule vague avant W9 qui a une place libre ; TK-16 garde la validation, le point d'envoi et l'expéditeur, et sa DoD (3) se vérifie sur le socle déjà fusionné ; (2) si la mesure de TK-22 dépasse 400 lignes, en sortir les limites en mémoire (Étape 9) en ticket complémentaire, dans une vague ajoutée entre W12 et W13, ce qui décale TK-24 d'une vague. Les deux tickets deviendraient des issues de plus sur le board.
- **Vocabulaire du journal** : le contrat demande une ligne par requête E-02, « qui nomme la vraie issue et rien d'autre », mais ne nomme pas cinq issues possibles : corps illisible, type de contenu refusé (`415`), type de réponse refusé (`406`), origine refusée, erreur interne. Le plan les ajoute (PB-05 : `unreadable-body`, `unsupported-media-type`, `not-acceptable`, `origin-refused`, `internal-error`), sans effet sur le front, pour qu'une requête POST sur la route de E-02 ait toujours sa ligne, même quand le contrat range sa réponse parmi les appels hors contrat (`415`, section 4). Il ajoute aussi à la ligne deux clés que le contrat ne prévoit pas : `durationMs`, la durée de traitement, qui montre un prestataire lent ou un réveil, et `providerStatus`, le code de réponse de Brevo lors d'un échec, qui distingue par exemple une clé refusée d'un appel mal formé ; aucune n'est une donnée personnelle. Le code HTTP et l'adaptateur d'envoi, redondants, ne sont pas écrits. Recommandation : accepter les cinq issues et les deux clés.
- **Corps trop gros** : refusé au-delà de 64 Kio par le `400` de corps illisible que le contrat définit déjà, plutôt que par un `413` qu'il ne prévoit pas (PB-06). Recommandation : accepter.
- **Limite par adresse IPv6** : une adresse IPv6 est comptée par son préfixe /64, que reçoit un même abonné, sinon un seul visiteur dispose de milliards d'adresses (PB-03). « Par adresse IP » se lit alors « par adresse IPv4 ou par préfixe /64 en IPv6 ». Recommandation : accepter.
- **En-tête de l'adresse IP chez Render** : non documenté ; un message de l'équipe de Render de 2021 et un constat d'utilisateur de 2024 se contredisent sur `X-Forwarded-For` (PB-08). Le plan rend l'en-tête et le rang réglables (PB-03) et fixe le constat en TK-24, sans code ni journal d'adresse (Étape 10). Recommandation : accepter cette procédure.
- **Docker sur l'instance gratuite de Render** : la documentation consultée liste l'offre gratuite pour un service web et décrit les services construits depuis un Dockerfile, sans dire en toutes lettres que les deux se combinent ; rien ne l'exclut. Recommandation : ouvrir le compte Render avant W13, comme prévu, et ouvrir la première PR de TK-24 dès le début de W13, pour le savoir au plus tôt.
